Methodology

Here is the methodology and background for how the numbers on the results page were made, the decisions motivating the experimental design, where the questions came from, what the two ratings mean and what was held identical between providers.

The questions

I took what I saw from run 1 to create a set of __N_QUESTIONS__ questions: __N_BASE__ ordinary, __N_HARD__ deliberately hard, __N_UNANS__ with no answer anywhere, designed to baseline false positives. Of course, there is a bias for the questions created based on the ones I picked.

They spread across six kinds of task: breaking news, how-to, product lookup, local and geographic, recent releases, and live numbers. Additionally, these spanned six subject areas, weighted toward software and everyday questions because that is what I actually point a retrieval agent at.

Every question carries a note written before the run saying what a correct page contains and what a plausible wrong one looks like, the judges never see those notes. They exist so that when a rating looks wrong in the explorer, there is a written intent to argue why.

What makes the hard hard

Four factors tend to make questions harder for search providers to serve. Trap: a plausible wrong answer sits close to the right one, an older figure or a superseded draft.
Buried: the answer exists but not on the first result.
Multi: no single page has all of it.
Obscure: the subject is thinly covered, so the index either has it or does not.

The point of the split is that easy questions make providers look alike, but as questions get harder, the gaps between providers comes up. A question your model could nearly answer unaided does not test retrieval much, and if a whole benchmark is built from those, every provider passes.

Why __N_UNANS__ questions with no answer

The point behind creating these unanswerable set was to create a group of questions to test how far these search providers try to cheat with results that can cause hallucinations for models and agents. Each of these asks about something that sounds entirely real and does not exist.

Correct behaviour is that every page rates 0 or 1. A page rated 2 or 3 means either a provider surfaced something that invented the answer or a judge invented the relevance.

What run 2 changed, and why

Run 1 asked 48 questions of four providers and graded the answer a model wrote from the results that were returned. Then it checked whether source quality and answer quality moved together. However, in that run there was only a correlation of 0.16, where 1 is lockstep and 0 is unrelated. The model was carrying most of the result.

So run 2 grades the sources instead, doubles the field to eight providers, and uses three judges from three different labs instead of one, so that no single model's taste skews the ranking. It also gives the slow arms room to finish rather than timing them out.

The two ratings

Two ratings, both on a 0 to 3 scale, asking different questions of the same results.

The page rating asks whether one page helps answer one question. The judge is never told which provider returned it, never shown an answer, and never asked to write one.

The set rating asks whether a whole set of __NUM_SOURCES__ results is enough to answer, and that is the headline on the results page.

These are separate judge calls, and the set rating is not an average of the page ratings. It cannot be. __NUM_SOURCES__ pages each holding a third of the answer and __NUM_SOURCES__ pages holding nothing average out to roughly the same score, and only one of those sets lets you answer the question.

Each judge scores on its own and nothing is merged before it gets recorded. Every individual verdict is in the explorer with the sentence that judge wrote for it. The averaging happens once, at the end, only so there is something to put in a table: a provider's set rating is the mean of its scores across all __N_QUESTIONS__ questions and all three judges.

Every score has a written definition rather than a number on its own, because two models can agree on what a 2 means but a bare scale is something each one invents its own version of.

Both prompts are in core/controls.ts in full. The set prompt replaced an earlier one partway through the run. That one graded whether sources looked good, fresh and authoritative and cleanly extracted, and on a question with no answer anywhere it handed out a passing score while the page judge was correctly rating every page 0 or 1. The sources were good. They just could not answer. Everything published here was scored with the replacement.

What varies

One question goes to all eight providers, each returns up to __NUM_SOURCES__ results, and nothing else changes between them. Same prompt, same judges, same number of results asked for, caching off.

__ARMS_DAY1__ of the eight arms finished inside one day. Tavily and Bright Data hit their own rate limits and finished in the early hours of the next morning, and that is the one place the arms were not treated the same: a page that changed overnight would have looked different to those two.

Every setting sits in one file, core/controls.ts, and every stage reads from it, so there is only ever one value of anything for a stage to find. Each provider was set to the best tier it sells, and where there was a depth or content knob it got turned up.

Serper is the one deliberate downgrade. It sells a separate scrape endpoint and this run does not call it, which I decided before the run rather than after seeing the scores. Bright Data is the only provider that needs a second paid product to get page text at all, and its extraction step missed roughly half the URLs it tried.

Pooling

Providers return the same pages constantly. Every page from every arm collapses into one pool keyed by normalised URL and gets graded once, and that rating counts for each provider that returned it. __OVERLAP_ONE__% of the __UNIQUE_PAIRS__ pages came from exactly one provider and __OVERLAP_ALL__ came from all eight.

Pooling also blinds the judge, which is a real argument for doing it: a page is detached from whoever returned it before anyone grades it, so there is no provider name to be swayed by. But it was a cost decision first and it costs something real. Where several arms returned the same URL, the longest extraction anyone returned is what got graded, so extraction quality is averaged away on those pages. With a bigger budget I would not pool.

The statistics, in words

Confidence interval

Where the real value probably sits, given that __N_QUESTIONS__ questions is a sample rather than everything. If two of them overlap, the order between those providers is not a finding.

Variance shares

Of everything that moves in the ratings, how much each thing explains. The provider explains __VAR_PROVIDER__%. Which judge you happened to pick explains __VAR_JUDGE__%.

Kappa

How much two judges agree, after subtracting the agreement you would get from two people guessing. These three run __KAPPA_LO__ to __KAPPA_HI__: they agree on the order and argue about the decimals.

Sign test

Compare two providers on the same small set of questions by counting wins, then ask how often a split that lopsided happens by luck. Used on the __N_UNANS__ unanswerable questions, where eight providers cannot be ranked but two can be compared.

What this cannot tell you

Who extracts a page best

Each source gets a __TRUNC_LIMIT__-character slice, which is what an agent with a real context budget would give it. A bigger slice would let the providers that return whole documents show more of what they extract, and it could reorder the bottom of the table. Pooling costs the same measurement a second way: on the __OVERLAP_MULTI_PCT__% of pages that several arms returned, the longest extraction anyone returned is the one that got graded. Measuring extraction properly means holding the URLs fixed and varying only the extractor, and I have not run that.

What your agent will answer

Nothing here grades an answer, on purpose. If that is what you want to know, an answer-graded benchmark measures it, bearing in mind such a number is also grading your model.

How any of this behaves at scale

Every arm ran once, at whatever concurrency it tolerated, so nothing here measures throughput, quota behaviour, or what any of it costs at volume. What the run did collide with is in notes from the run: a provider that throttles at one request, a plan that ran out mid-way, a day that ate most of a month's credits. Those happened once each. None of them is a measurement.

Whether the questions look like yours

They are written rather than collected from real traffic, and I wrote all of them. The harness exists so you can run your own instead, which is the only real answer to this one.

Whether tomorrow would come out the same

This is one run, fetched __FETCHED__. Every provider is a moving target: indexes change, tiers change, and the model behind one of these can be swapped without anyone telling you. Nothing here is measured twice, so none of these numbers carries an estimate of how far it would move on a re-run. The confidence intervals describe sampling across questions inside this one run, which is a narrower claim than it looks.

Whether the judges are right

Three language models grade every page and they agree with each other well enough to trust the ranking, kappa __KAPPA_LO__ to __KAPPA_HI__, which is moderate on a four-point scale. That is agreement among themselves, not agreement with a person. They were calibrated against human-settled pairs before the run, but three models trained on overlapping text can share a blind spot and agree anyway, and the __N_UNANS__ unanswerable questions show exactly that: a plausible near-miss fools some of them.

How fast any of them are for you

The table has a median latency column, so timing is measured, but it is measured from one machine on one network over two days. A provider that is quick from my connection may not be quick from your region. Take the ordering seriously and the absolute numbers loosely.

Every rating is published with the sentence the judge wrote to justify it. Any number here traces back to the verdict that produced it.
