Search APIs, graded on their sources

Benchmarks of search APIs grade the answer a model writes afterwards, a number that is mostly a score of the model. With Sourcery I wanted to control for the LLM and judge purely on the fetched results. All eight providers got the same __N_QUESTIONS__ questions in a single run, then 3 models — Claude Sonnet 5, GPT-5.6 and GLM 5.2 — read every page and scored it on a 0–3 scale.

Why it is built this way

Some of what follows is a principled choice and some of it is my budget. They are worth telling apart, so here is which is which.

Pooling was a cost decision first. Every page is graded once and that rating counts for every provider that returned it. There is a real methodological argument for it — a page is detached from whoever returned it before anyone grades it, so there is no provider name for a judge to be swayed by — and I would make that argument honestly. But I picked it because the eight arms returned __N_PAIRS__ question-page pairs that collapse to __UNIQUE_PAIRS__ unique ones, and grading the unique set meant __POOL_SAVED_PCT__% fewer judge calls. I could not have afforded the run otherwise. What it costs is real and I would rather you hear it from me: where several arms returned the same URL, the longest extraction anyone returned is the one that got graded, so extraction quality is averaged away on those pages.

The __TRUNC_LIMIT__-character cut on each source is the same story. It is a realistic slice of an agent's context budget, which is true, and it is also the cheapest way to make __N_RATINGS__ ratings affordable. A bigger budget would have cost more and might have reordered the bottom of the table.

Three judges, not five. Five models passed calibration against human-settled pairs and none of them rated a keyword-stuffed page above zero. I ran three of them, because three was what I could pay for. And this is one run on one set of questions — nothing here is measured twice, so no number on this page carries an estimate of how much it would move if I ran it again.

Results

Each provider gave back eight pages per question, and a judge saw all eight together and answered one question: could you answer from these alone? Zero means nothing useful, three means a full answer. That is the set rating, and it is the headline on this page — it grades the eight results as a set, not one page at a time.

Perplexity is clear of everyone else. Below it there are two groups, and inside either one the order doesn't mean anything — ask again next week and they could come back in a different sequence. The gap between the two groups is the actual result: Exa to Tavily is four tenths of a rung, bigger than anything inside either cluster.

Throw the scale out entirely and you get the same thing. Perplexity returns a page that fully answers the question __PPX_RUNG3__% of the time, Bright Data manages __BD_RUNG3__%, and the ordering doesn't move — so none of this rests on the 0–3 rubric being right.

Base vs. hard questions

I wrote half the set to be hard: multi-hop, ambiguous, or needing a source that isn't the first result.

This chart is the page rating, not the set rating above — it scores each page on its own rather than the eight together. That is why the order is different: Exa's individual pages beat Parallel's, while Parallel's eight fit together better and win on the set.

Benchmark search on questions your model could nearly answer on its own and every provider looks fine. The difference only shows up on the ones you actually needed help with.

The chart is ordered by its own numbers, so Exa sits above Parallel here. Both orderings are real and they are measuring different things — and since the two are inside each other's confidence intervals on the set score, they tie on the headline either way.

Cost

The three providers on the cheapest tier take three of the top four places; the outright cheapest places sixth. Serper matches Tavily at a fifty-fourth of the cost. It returns links and snippets and never page content, so if you already run a scraper, that is the part you were paying extra for.

Returned content

Brave is the one to look at. It ranks second and returns real page text on one per cent of results, and its content is search snippets joined together. Fine for grounding a summary, useless to an agent that has to read a document. Exa keeps headings and drops links. Bright Data keeps nearly every image and no tables.

The other axis is volume. An agent gives each source a slice of its context, and this run allows __TRUNC_LIMIT__ characters, which is a realistic budget. __TRUNC_FIRECRAWL__% of Firecrawl's pages run past it; __TRUNC_PERPLEXITY__% of Perplexity's do. Firecrawl returns whole documents and Perplexity returns excerpts, and past the budget that difference stops reaching the model.

Why this disagrees with answer-graded indexes

Artificial Analysis published a search index the day before this went out. It ranks Firecrawl third. This run puts it seventh. The two measure different things.

They grade what an agent eventually produces: up to 25 turns and roughly nine to thirteen searches per task, and then the final answer gets scored, so a weak first result set just gets repaired by searching again. Sourcery grades what one search hands back — eight results, one shot, no recovery. Their questions are static obscure facts, mine lean fresh.

Neither index rewards Firecrawl's extraction, for opposite reasons. Their settings disable its scraping by name and route everyone through one generic extractor. This run asked for full page markdown, got it, and then metered every source to the same context budget, which most of those pages exceed. The advantage is real and sits upstream of where either benchmark can see it.

Their index carries no confidence intervals and their top five span two points. On their published sample sizes that gap is inside the noise, which is the same reason three providers here are drawn as a tie.

Six providers, six jobs

What you're building decides this more than the ranking does. Three of these eight are tied on the headline and they still aren't interchangeable — one returns whole documents, one returns snippets, one returns prose with the links stripped out. So pick on the job.

Perplexitybest overall

Clear of the field and on the cheapest tier. Fully answers __PPX_RUNG3__% of the time, about 1.4× anyone else. Returns excerpts rather than whole pages, and it is the easiest of the eight to fool.

Serperbest raw search

Links and snippets, no page content, __SERPER_PRICE__ a query. Matches Tavily's score at a fifty-fourth of the price. The right answer if you already have a scraper and only need the index.

Tavilybest for an agent that reads documents

Full page markdown on __TAVILY_MD__% of results, with headings, links and images intact. Outscores Firecrawl and costs less. If your agent needs the document rather than a summary of it, start here.

Exabest clean prose

Keeps structure and strips navigation: __EXA_HEADINGS__% of its pages have headings, __EXA_LINKS__% have links. Top-cluster relevance. Good when you are feeding text to a model and link noise costs you context.

Firecrawlhardest to fool

On the __N_UNANS__ questions with no answer, it produced the fewest convincing near-misses, beating Perplexity on all __N_UNANS__. That has to be read next to its seventh place overall, though, because it returns fewer good pages than the others and so has fewer chances to return a convincing wrong one. Most expensive of the eight.

Bravesummaries only

Ranks second on relevance and returns real page text on __BRAVE_MD__% of results, and its content is search snippets joined together. Fine for grounding a summary, wrong for anything that has to read a page.

Hallucinated relevance

Perplexity is the best of the eight at finding real answers and the worst at not manufacturing the appearance of one. Asked for the default of max_parallel_vacuum_workers, a Postgres setting that does not exist, one arm came back with a page documenting max_parallel_maintenance_workers — a real setting, with a real default — and a judge read that as a direct answer to the question. It indicts the judges as much as the provider: one of the three marked the page down and said the parameter name did not match, and the other two did not. Your code can see an empty result and handle it; it cannot see a confident near-miss. If your agent has no way to check what it is told, weigh that above the ranking.

What varies

One question goes to all eight providers. Each returns up to __NUM_SOURCES__ results. Nothing else differs between arms: same prompt, same judges, same number of results requested, caching off. Of the eight arms, __ARMS_DAY1__ finished inside a single day. Tavily and Bright Data ran into their own rate limits and finished in the early hours of the next morning, and that is the one respect in which the arms were not treated identically — a page that changed overnight would have been seen differently by those two.

The settings live in one file, core/controls.ts, and every stage imports from it, so there is only ever one value of anything for a stage to read.

The two rubrics

Both ask the same question at two scopes, on the same four rungs. Two models can agree on a named rung; a bare number on a wide scale is something each one invents its own version of.

Page rating — does this page help?

One question, one page. The judge is never told which provider returned it, never shown an answer, and never asked to write one.

__PAGE_RUNGS__

Set rating — could someone answer from these alone?

The headline. A per-page average cannot answer this: eight pages each holding a third of the answer and eight holding nothing average out the same.

__SET_RUNGS__

Both prompts are in core/controls.ts in full. The set prompt replaced an earlier one partway through the run, which graded whether sources looked good: fresh, authoritative, cleanly extracted. On a question with no answer anywhere it returned a passing score while the page judge rated every page 0 or 1. The sources were good, they just could not answer.

Provider settings

Every provider was set to the highest-quality tier it offers. Where a depth or content knob existed it was turned up.

Pooling

Providers overlap heavily. Every page from every arm is collapsed into one pool keyed by normalized URL and graded once; that rating counts for each provider that returned it. __OVERLAP_ONE__% of the __UNIQUE_PAIRS__ pages came from exactly one provider and __OVERLAP_ALL__ came from all eight.

Pooling blinds the judge structurally: a page is detached from whoever returned it before grading, so there is no provider name to be swayed by. The cost is that where several arms returned the same URL, the longest extraction anyone returned is what gets graded, so extraction quality is averaged away on those pages.

The statistics, in words

Confidence interval

Where the real value probably sits, given that __N_QUESTIONS__ questions is a sample. Two overlapping intervals mean the order between those providers is not a finding.

Variance shares

How much of everything that varies is explained by each thing that could explain it. The provider explains __VAR_PROVIDER__%; which judge you picked explains __VAR_JUDGE__%.

Kappa

Agreement between two judges after subtracting the agreement you would get by chance. These three run __KAPPA_LO__ to __KAPPA_HI__ — they agree on the order and argue about the decimals.

Sign test

Comparing two providers across the same small set of questions by counting wins, then asking how often a split that lopsided would happen by luck. Used on the __N_UNANS__ unanswerable questions, where eight providers cannot be ranked but two can be compared.

What this cannot tell you

Who extracts a page best

Each source gets a __TRUNC_LIMIT__-character slice, which is what an agent with a real context budget would allow. Providers that return whole documents therefore have most of that document sitting past the line. Other budgets are just as defensible. A larger slice would let the providers returning whole documents show more of what they extract, and it could reorder the bottom of the table, though it would not close the gap at the top. Pooling costs the same measurement a second way — where several arms returned the same URL, the longest extraction anyone returned is the one that got graded, and that is __OVERLAP_MULTI_PCT__% of the pages. Measuring extraction properly means holding the URLs fixed and varying only the extractor, and that run has not happened.

What your agent will answer

Nothing here grades an answer, on purpose. An answer-graded benchmark measures that, bearing in mind such a number also grades your model.

How any of this behaves at scale

Every arm was run once, at whatever concurrency it tolerated, so nothing here measures throughput, quota behaviour, or what any of these costs at volume. What this run did collide with — a provider that throttles at one request, a plan that ran out mid-way, a day that ate most of a month's credits — is written up in . Those are things that happened once; none of them is a measurement.

Whether the questions look like yours

__N_QUESTIONS__ questions written to probe retrieval, not collected from real traffic: __N_BASE__ ordinary, __N_HARD__ deliberately hard, __N_UNANS__ with no answer at all. I wrote all of them, so whatever I find interesting is in the sample and whatever I did not think to ask is not. Frozen and public, so you can judge the resemblance — and the harness exists so you can run your own instead.

Whether tomorrow would come out the same

This is one run, fetched __FETCHED__. Every provider is a moving target: indexes change, tiers change, and a model behind one of these can be swapped without telling you. Nothing here is measured twice, so none of these numbers carries an estimate of how much it would move on a re-run. The confidence intervals describe sampling across questions within this one run, which is a narrower claim than it looks.

Whether the judges are right

Three large language models grade every page, and they agree with each other well enough to trust the ranking — kappa __KAPPA_LO__ to __KAPPA_HI__, moderate on a four-point scale. That is agreement among themselves, not agreement with a person. They were calibrated against human-settled pairs before the run, but three models trained on overlapping text can share a blind spot and agree anyway, and the __N_UNANS__ unanswerable questions show one: a plausible near-miss fools some of them.

How fast any of them are for you

The table has a median latency column, so timing is measured — but it is measured from one machine on one network over two days, and a provider that is quick from my connection may not be quick from your region. Each arm ran at whatever concurrency it tolerated, which does not flatter the slow end: __LAT_SLOW__ throttles above a single concurrent request, so it ran with less contention than anyone and is still the slowest by a wide margin. Take the ordering seriously and the absolute numbers loosely.
