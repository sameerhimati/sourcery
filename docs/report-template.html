Search APIs, graded on their sources

Every published benchmark of a search API grades the answer a language model writes after reading the results. That number is mostly a score of the model. This one never looks at an answer. Eight providers, the same __N_QUESTIONS__ questions on one day, and __N_JUDGES__ judges reading every one of the __UNIQUE_PAIRS__ pages that actually came back — __N_RATINGS__ ratings in all.

__STATS__

Two ways to grade a search API

The usual way is end to end. Give an agent a hard question and a search tool, let it run, and score the answer it produces against a known one. It is a real measurement and it has an obvious appeal: the answer is the thing you wanted.

The problem is what else is in that number. A capable model answers a lot of questions from what it already knows. When a benchmark of this kind publishes its no-search baseline — the same model, same questions, no search tool at all — that baseline can land near half the winning score. Artificial Analysis’s search index, published the day before this page, scores 33 for the model alone against 75 for its top-ranked provider. So a third of the result was never about retrieval. The search provider is being graded through a filter that is itself doing much of the work, and a provider that returns nothing useful can still ride a confident model to a passing answer.

An earlier version of this project measured both sides on the same queries and found they barely move together — the correlation between how good the fetched sources were and how good the final answer scored was 0.16. Ranking providers by answer quality mostly ranks your own model.

So this measures the other half. A judge sees one question and one page and answers a single question: does this page help? Nothing else. It is never asked what the answer is, never shown a draft, and never allowed to fill a gap from memory, because it has no gap to fill. What comes out is a score for the retrieval layer on its own.

Neither number replaces the other. An answer-graded benchmark tells you what an agent built on a provider ends up producing, with real reference answers behind it. This tells you what the provider actually handed over. If you are choosing a search API and you only look at the first kind, you cannot tell a good index from a good guesser.

What was measured

__N_QUESTIONS__ questions, frozen before the run: __N_BASE__ ordinary ones, __N_HARD__ written to be hard, and __N_UNANS__ with no answer anywhere as an honesty check. Each went to all __N_PROVIDERS__ providers on the same day with caching off — __N_SEARCHES__ searches in total. Everyone was asked for eight results, so nobody wins by returning more.

Every page that came back went to the same __N_JUDGES__ judges, each from a different lab, and each scored it 0 to 3: nothing useful, on topic but useless, part of the answer, answers it. That is __N_RATINGS__ ratings. Then each provider's whole set of eight pages went to those same judges with a different question — could someone answer from these alone? — for another __N_SETS__ verdicts.

The set score is the headline, and the reason is worth a sentence. Averaging the pages cannot tell you whether a set is any good: eight pages each holding a third of the answer and eight pages holding nothing average out the same. Only the whole set answers a question.

The result

One provider is clear of the field. After that, the ranking mostly stops being a ranking.

Perplexity leads and its interval clears everyone else's. Below that there are two groups and no order inside either: Brave, Parallel and Exa are one, and Tavily, Serper, Firecrawl and Bright Data are the other. Run the same questions again next week and the members of each group could come back in a different sequence. That is not a hedge, it is the measurement — and it is the part that a table of eight ranked rows is built to hide.

What is real is the step between the groups. The gap from Exa to Tavily is four tenths of a rung, larger than anything inside either cluster, and it is the only place in the table where the choice clearly changes what you get.

Easy questions hide the difference

Half the set was written to be hard on purpose — multi-hop, ambiguous, or needing a source that is not the first result. The providers at the top barely notice. The ones at the bottom fall away.

This is the practical warning in the whole run. Benchmark search on questions your model could nearly answer already and every provider looks adequate, because the easy half compresses them together. The difference between these products only shows up on the questions you actually needed help with.

Price buys nothing

The same __N_QUESTIONS__ questions cost twenty cents through the cheapest provider and seventeen dollars through the most expensive. The quality ordering does not follow the price ordering anywhere.

The three arms sharing the cheapest per-query tier take three of the top four places, and the outright cheapest provider of all places sixth — price predicts nothing in either direction. Serper matches Tavily's score at a fifty-fourth of the price, which is less surprising than it sounds once you know what Serper does: it returns links and snippets and never page content. If you already run a scraper, that is the whole product you were paying extra for.

“Page text” means something different to each of them

Two providers can both return a page and hand you completely different things. None of this appears in a relevance score, and it decides what you can build on top.

Brave is the one to look at. It scores well on relevance and returns real page text on one per cent of results — what it hands back is search snippets joined together, entities still undecoded, fragments ending in the result page's own ellipsis. That is fine for grounding a summary and useless to an agent that has to read a document. Exa keeps structure and drops links. Bright Data keeps almost every image and no tables. A crawler built on the wrong one of these fails for reasons that never show up in a score.

What to use

Best overall
Perplexity

The only provider clear of the field, and on the cheapest tier. Returns a page that fully answers about half the time, roughly 1.4× anyone else.

Best value
Serper

Tavily's score at a fifty-fourth of the price. Links and snippets only — pair it with your own fetch instead of paying for bundled extraction.

Hardest to fool
Firecrawl

On the __N_UNANS__ questions with no answer, it produced the fewest convincing near-misses, beating Perplexity on all __N_UNANS__. Nothing downstream catches that error.

Read the fine print
Brave

Ranks second and is not returning pages. Choose it to ground a summary; do not choose it for an agent that has to read a document.

The trade-off worth naming: Perplexity is the best of the eight at finding real answers and the worst at not manufacturing the appearance of one. Asked for a Postgres setting that does not exist, one arm returned a page about a real setting with a similar name and a judge called it a direct answer. For an agent, that failure is more expensive than a miss, because a miss is visible and a confident near-miss is not.

Where this run is gated

Everything below either limits what the numbers mean or limited what the run could do. None of it is buried in a footnote because all of it changes how much weight the results carry.

Every source was cut to __TRUNC_LIMIT__ characters

That cut bound on __TRUNC_FIRECRAWL__% of Firecrawl's pages and __TRUNC_PERPLEXITY__% of Perplexity's, so a 40KB article and __TRUNC_LIMIT__ characters of stitched snippets reached the judge at the same length. This measures which pages you get back and is blind to how deeply a provider extracts them. For Firecrawl that is the result rather than a caveat beside it: extraction is what it sells, and this run does not test it.

Plan limits shaped the run, not just the bill

Bright Data throttles above one concurrent request, so its pass ran slowly enough to cross midnight and needed a repair round. Tavily's plan ran out around question 150 and also needed a second pass. Firecrawl consumed 3,493 credits in a single day, about seventy per cent of a 5,000-credit month, bought for $25 — against the $17.47 list-rate figure in the table above, which is what the run would cost at the published per-query price rather than what was actually paid for the credits. A keyless control arm was dropped entirely after eight consecutive captcha failures and no successes. The retrieval bill was $__COST_TOTAL__ in total, and the ceiling on a run like this is a rate limit long before it is money.

Providers overlap, and a page is graded once

The same page often comes back from several providers. It is judged once and that rating counts for everyone who returned it, using the longest version anyone returned. __OVERLAP_ONE__% of the __UNIQUE_PAIRS__ unique pages came from exactly one provider and only __OVERLAP_ALL__ came from all eight, so these indexes overlap much less than you would guess — but a provider is not scored on its own extraction of a shared page.

__N_UNANS__ questions is a small sample

The unanswerable set is __N_UNANS__ questions, which is enough to compare two providers against each other across all __N_UNANS__ and not enough to rank eight. Firecrawl beating Perplexity on every one of them holds up; the ordering of the middle of that table does not, and it is not presented as one.

Swap the judge and every number moves

Which judge you pick accounts for __VAR_JUDGE__% of the variation and the provider accounts for __VAR_PROVIDER__%. Pairwise agreement runs kappa __KAPPA_LO__ to __KAPPA_HI__, which is moderate. The ranking survives the swap; the absolute values do not, so read the gaps and not the decimals.

Nobody abstains

All eight returned a full set of results on the questions with no answer, exactly as they do everywhere else, and there were zero empty results across the run. Deciding there is nothing to find is the caller's job. None of these products will do it for you, and none of them exposes a confidence score you could threshold on.

Sourcery is an open-source harness, not a leaderboard service. The questions here are frozen so these numbers stay comparable, but the point of shipping it is that you can run the same comparison on the queries you actually care about, with your own keys and your own judge.

Every rating on this page is published with the sentence the judge wrote to justify it, and every figure is generated from a derived data file that is committed alongside the raw verdicts. Any number here can be traced back to the verdict that produced it without taking anyone's word for it.
